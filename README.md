# LBP2900 Print

Print to a **Canon LBP2900** from an Android phone over a USB OTG cable. No
PC, no print server, no root.

> **Status: not yet tested against real hardware.** The compression and the
> command sequence are verified against the reference C driver (details
> below), but nobody has yet plugged a phone into an actual LBP2900 and
> pressed Print. Expect to iterate. The app is built to make that iteration
> easy — everything it does is on screen and copyable.

## Why this app has to exist

The LBP2900 is a "winprinter". It understands no page description language
at all — no PCL, no PostScript. The host must rasterise every page to a
600dpi 1-bit bitmap, compress it in Canon's proprietary **HiSCoA** format,
and then hold a stateful two-way USB conversation with the printer (CAPT
2.1) to get it onto paper.

Generic Android printing apps assume the printer speaks PCL or ESC/P. They
send bytes it cannot parse, which is why they produce blank sheets, jams,
or pages of garbage. There is no generic fix — an app has to implement CAPT
specifically. That is what this is.

## Getting an APK

You do not need Android Studio or any local toolchain. GitHub builds it.

1. Create a new **private** repository on GitHub.
2. Push this project to it (or upload the files through the web UI).
3. Open the **Actions** tab. The `Build APK` workflow runs automatically on
   push; if it does not, click it and press **Run workflow**.
4. When it finishes, open the run and download the **lbp2900-print-debug**
   artifact from the Artifacts section at the bottom.
5. Unzip it, transfer the `.apk` to your phone, and install it. You will
   need to allow "install unknown apps" for whatever app you use to open it.

The build also runs the protocol verification suites first, so a red run
means something is wrong with the driver logic, not just the packaging.

There is deliberately no Gradle wrapper committed. If you later open the
project in Android Studio it will offer to add one, or you can run
`gradle wrapper` once with a network connection.

## Using it

1. Power on the printer and connect it to your phone with a USB OTG
   adapter. The printer is mains-powered, so it draws essentially nothing
   from the phone.
2. Android should offer to open **LBP2900 Print**. If not, launch it
   manually.
3. Pick a PDF, or share a PDF to the app from anywhere else.
4. Press **Print**, grant the USB permission when asked, and watch the log.

Currently A4 only, single-sided, 600dpi.

### When it goes wrong

Press **Copy log** and keep the text. The log records every command sent,
every reply, and every status poll, which is enough to tell exactly where
the conversation broke down. Useful things to note alongside it: what the
printer's LED was doing, and whether any paper moved.

## What is actually verified

The parts that could be checked without hardware, were:

| Component | How it was verified |
|---|---|
| HiSCoA compressor | 13 golden vectors generated by linking captdriver's own C compressor, compared byte for byte. Covers the long-run escape, the byte cache, both end-of-band types, and a realistic 70-line A4 band. |
| Page geometry | Taken from CUPS itself — captdriver's `canon-lbp.drv` compiled with `ppdc`, then run through `cupsRasterInterpretPPD()`, the same call a real print job makes. Not estimated. |
| Command sequence | The full job state machine driven against a scripted fake printer, asserting command order, framing, status parsing, and the exact 40-byte A4 page-parameter block. |

Not verified, and where trouble will be found: USB endpoint handling, the
PDF rasteriser's scaling and dithering, and every real-world timing
assumption in the status polling.

Run the checks yourself with `gradle :capt-core:check`.

## Things that will bite, and why they are written the way they are

Three details are counter-intuitive enough that "cleaning them up" will
break printing. Each is commented in the source; summarised here so they
survive a future rewrite.

- **`lineSize` is not the raster width.** It is the page width in *points*
  (595 for A4), which happens to sit 4 bytes above the real line length of
  591. The raster is centred inside that wider line, giving a 2-byte left
  shift. The printer is told 595, so "correcting" this skews every scanline.
- **HiSCoA origins are unsigned.** `origin[2]` is `lineSize - 7`, which
  underflows to a huge value on narrow bands; C's unsigned comparison then
  skips the match. Signed comparison reads off the end of the buffer.
- **The final bit padding is unconditional.** When the stream is already
  32-bit aligned it emits a whole extra 32 bits. Upstream has that `if`
  commented out deliberately.

One place this port intentionally *differs* from upstream is status
decoding: captdriver's length guards compare against the full frame length
while indexing the payload, so short replies over-read its static buffer.
Harmless in C, fatal in Kotlin. See the comment in `CaptStatus.decode`.

## Layout

```
capt-core/          Pure Kotlin, no Android dependencies
  HiScoa.kt           Band compressor
  CaptCommand.kt      Command codes
  CaptSession.kt      Frame encode/decode over any byte pipe
  CaptStatus.kt       Status block and flags
  CaptTransport.kt    The pipe interface
  Lbp2900Job.kt       Job/page state machine
  BandCompressor.kt   Raster -> compressed bands
  PageGeometry.kt     Page dimensions and parameters

app/                Android layer
  UsbCaptTransport.kt Transport over USB host bulk endpoints
  PdfRasterizer.kt    PDF -> 1bpp, strip by strip, Floyd-Steinberg
  PrintController.kt  Wires it together
  MainActivity.kt     Picker, Print button, log

tools/genvectors.c  Regenerates the golden vectors against captdriver
```

`capt-core` deliberately knows nothing about Android. The same code can
drive a network socket instead of a USB endpoint, which is the path to an
ESP32-S3 acting as a wireless bridge — the phone would rasterise and
compress exactly as it does now, and only the transport would change.

## Roadmap

1. Get one page out of the printer.
2. Android `PrintService`, so the printer appears in the normal
   Share → Print dialog instead of needing this app opened.
3. More paper sizes. Only A4 has real-world confirmation; the other size
   codes come from the driver's table but have never been exercised,
   because a bug upstream means CUPS always sends A4's code regardless.
4. Optional Wi-Fi transport for an ESP32-S3 bridge.
